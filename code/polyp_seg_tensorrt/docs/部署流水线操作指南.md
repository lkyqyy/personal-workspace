# 部署流水线操作指南

本文档把本 demo 的实践抽象成**可复用的流水线**：以后遇到「模型转换 → C++ 推理 → 精度对齐 → 性能分析 → 压测」类似问题时，可按阶段逐步完成，知道要做哪些事、产出什么、常见坑在哪。适用于其他分割/检测模型、其他 TensorRT/ONNX 部署场景。

---

## 流水线总览

```mermaid
flowchart LR
    A[1. 模型与数据] --> B[2. 导出]
    B --> C[3. C++ 推理骨架]
    C --> D[4. 精度对齐]
    D --> E[5. 性能分析]
    E --> F[6. 压测与健壮性]
    F --> G[7. 文档与开源]
```

| 阶段 | 目标 | 本 demo 对应 |
|------|------|----------------|
| 1 | 模型与数据就绪 | train/snapshots、data/images&masks、scripts 准备脚本 |
| 2 | 导出 ONNX / TensorRT engine | export_pt_to_onnx、export_onnx_to_engine |
| 3 | C++ 能跑通单帧 | InferenceEngine、Preprocessor、Postprocessor、main 锚点/单图 |
| 4 | Python 与 C++ 结果一致 | 前后处理对照、锚点校验、验证集 Dice/IoU |

| 6 | 长时间与异常输入不崩 | --stress、--stress-robustness、nvidia-smi |
| 7 | 别人能复现、能开源 | README、LICENSE、.gitignore、文档索引 |

## 1. 模型与数据准备

**目标**：有可用的 PyTorch 模型（.pt）和验证集，目录与脚本约定好，便于后续导出和 C++ 校验。

**要做的事**：
- 训练或拿到 checkpoint（.pt），输入/输出尺寸、归一化、后处理（如 sigmoid）与训练时一致。
- 准备验证集：图像 + 标注（本 demo 为 mask），划分与训练一致，放到固定目录（如 `data/images`、`data/masks`）。
- 若有现成训练脚本，抽离「数据划分、路径」为配置或小脚本，保证 Python 评估与 C++ 用同一套 val。

**产出**：`models/xxx.pt`、`data/images/`、`data/masks/`（或等价结构），以及「如何从原始数据得到这些」的简短说明。

**常见坑**：验证集划分不一致导致 Python/C++ 对比的不是同一批图；输入尺寸/归一化与导出时不一致。

**本 demo**：`train/snapshots/best.pth`，`scripts/prepare_val_for_cpp.py` 生成 `data/images`、`data/masks`；见 `scripts/README.md`。

---

## 2. 导出（PyTorch → ONNX → TensorRT）

**目标**：得到 ONNX 和 TensorRT engine，输入/输出 shape、dtype、是否含 sigmoid 等与 C++ 侧约定一致。

**要做的事**：
- **PyTorch → ONNX**：固定输入 shape（如 1×3×H×W），决定输出是否带 sigmoid/softmax；必要时用 onnxsim 简化；检查 ONNX 的 input/output 名称与 shape。
- **ONNX → TensorRT engine**：按目标精度（FP32/FP16）转 engine；若动态 shape，设置 min/opt/max；记录实际用的 input size（如 256×256），C++ 侧一致。
- **可复现**：记录 ONNX 版本、TensorRT 版本、CUDA 版本；engine 与 GPU/TRT 版本绑定，换环境需重导。

**产出**：`models/xxx.onnx`、`models/xxx_fp16.engine`（等），以及「导出命令与关键参数」的文档或脚本注释。

**常见坑**：ONNX 输出带 sigmoid 而 C++ 又算一次；输入 H/W 或归一化与 C++ 不一致；动态 shape 未设 opt/max 导致 engine 不可用。

**本 demo**：`scripts/export_pt_to_onnx.py`（--sigmoid、--height/--width）、`scripts/export_onnx_to_engine.py`（--fp16）；`scripts/check_onnx_has_sigmoid.py` 检查输出；见 `docs/导出ONNX之后_C++_TensorRT推理准备.md`、`docs/导出脚本_写代码逻辑.md`。

## 3. C++ 推理骨架

**目标**：能加载 engine、读一张图、做前处理 → 推理 → 后处理，得到与 Python 同语义的 mask/结果；先不求性能，先求跑通。

**要做的事**：
- **加载**：读 .engine 文件，反序列化得到 Runtime/Engine/Context；按 engine 的 binding 分配 GPU 显存（input/output）；记录 input 的 N/C/H/W。
- **前处理**：与 Python 完全一致（resize 方式、letterbox、归一化 mean/std、HWC→CHW、dtype）；输出一块连续的 float 指针供 TensorRT 输入。
- **推理**：Host→Device 拷贝 → setInputShape（若动态）→ enqueueV2 → Device→Host 拷贝 → stream sync。
- **后处理**：与 Python 一致（裁 padding、二值化阈值、resize 回原图）；输出 cv::Mat 或等价结构。
- **入口**：main 里可先「单图路径 → 输出 mask」或「锚点 bin 输入 → 裸数据对比」，便于下一步精度对齐。

**产出**：可执行程序，能从命令行读图、输出 mask；或读固定 input/output bin 做逐元素对比。

**常见坑**：resize 与 Python 不一致（如 PIL vs OpenCV 坐标映射）；归一化顺序或 mean/std 写错；CHW 与 HWC 搞反；动态 shape 未 setInputShape。

**本 demo**：`InferenceEngine::load/predict/predictRaw`，`Preprocessor::process`（PIL 风格 resize），`Postprocessor::process_with_info`；main 支持锚点校验、单图、--first-5；见 `docs/推理流程与优化说明.md`、`docs/Python与C++前后处理对照.md`。

## 4. 精度对齐

**目标**：Python 与 C++ 在「同一批输入」上结果一致（或差异在可接受范围），避免部署后 silently 掉精度。

**要做的事**：
- **前后处理对照**：逐项列出 Python 与 C++ 的 resize、crop、归一化、二值化、数据布局，写成对照表；不一致处改 C++ 或改 Python 导出（推荐改 C++ 对齐 Python）。
- **锚点校验**：用 Python 导出若干张图的 input tensor 和 output tensor（raw logits 或 sigmoid 后，与 C++ 约定一致），C++ 读同一批 bin，predictRaw 后逐元素对比（MAE 或 max diff）；阈值可放宽（如 1e-2）以兼容 FP16/不同实现。
- **验证集 Dice/IoU**：同一验证集上，Python 与 C++ 端到端跑 mask，算 mean Dice、mean IoU；若差一截，回到「前后处理对照」和「sigmoid 是否重复」排查。
- **单图 debug**：对少数几张图，Python 与 C++ 各输出中间结果（input tensor、output tensor、mask），对比文件或脚本对比，快速定位哪一阶段不一致。

**产出**：对照文档、锚点通过结论、验证集 Dice/IoU 数值（及可接受范围）；必要时单图 debug 脚本与样例输出。

**常见坑**：ONNX 带 sigmoid 而 C++ 又算；resize 实现不同导致边缘差异；锚点用错（如 Python 输出概率、C++ 输出 logits）；阈值过严（1e-5）导致 FP16 误报失败。

**本 demo**：`docs/Python与C++前后处理对照.md`；`scripts/generate_anchor_data.py` + main 锚点校验；`scripts/compare_val_set.py`、`scripts/compare_debug_outputs.py`；Preprocessor 中 PIL 风格 resize；见 `docs/单元测试说明.md`（Preprocessor/Postprocessor 单测辅助一致性）。

## 5. 性能分析

**目标**：知道端到端和各阶段（前处理、推理、后处理）的耗时与占比，找到瓶颈，指导后续优化。

**要做的事**：
- **分阶段计时**：在 C++ 里对「前处理 / 推理 / 后处理」分别打点（或 predictWithTiming），得到每阶段 ms；汇总为 mean/std、占端到端比例。
- **Benchmark 模式**：对验证集或固定图集跑 N 轮（或 N 张×M 轮），统计各阶段均值、标准差、总耗时、FPS；输出表格和「瓶颈阶段」结论。
- **文档**：把「如何跑 benchmark、如何解读输出、典型数值范围、优化方向」写进文档，便于复现和对比。

**产出**：可复现的 benchmark 命令与输出示例、性能瓶颈说明文档（含优化建议）。

**常见坑**：计时包含不该包含的（如读图、分配）；只跑一张图或很少轮导致波动大；未 warmup 导致首帧偏慢。

**本 demo**：`InferenceEngine::predictWithTiming`、main 的 `--benchmark [轮数]`；`docs/性能瓶颈分析说明.md`（三阶段、占比、实测参考、优化建议）。

## 6. 压测与健壮性

**目标**：长时间运行不崩、显存不涨、异常输入不挂；吞吐/延迟稳定，P99 可接受。

**要做的事**：
- **吞吐与延迟**：用验证集或固定图循环跑 N 秒，统计总帧数、FPS、每若干帧采样一次端到端延迟，算 mean/P99/max；必要时按分钟输出 FPS，观察是否随温度/时间下降。
- **显存**：另开终端 nvidia-smi 或脚本周期采样；长时间跑后显存应稳定，若持续上升则排查泄漏（cudaFree、context 释放）。
- **异常输入**：空图、0 尺寸、超大尺寸、全黑/全白等，调用 predict 时期望返回 false 或不崩溃；可做小工具或 --stress-robustness 逐项测并输出 PASS/FAIL。
- **输入防护**：在推理入口统一校验（空、尺寸范围），避免 letterbox 除零或 OOM。

**产出**：压测命令与示例输出（FPS、P99、Errors）、显存观察方法、异常输入测试列表与结果；入口处输入校验与文档说明。

**常见坑**：只跑几秒看不出显存泄漏；异常输入未防护导致崩溃；P99 与 mean 差很多未关注。

**本 demo**：main 的 `--stress [秒数]`（延迟采样、按分钟 FPS、nvidia-smi 提示）、`--stress-robustness`；InferenceEngine 的 isValidInput（空/0/超 8192）；`docs/性能瓶颈分析说明.md` 第 5 节（四维压测）。

## 7. 文档与可复现（开源准备）

**目标**：别人能按文档从零构建、跑通、复现结果；若开源，符合常见习惯（README、LICENSE、.gitignore）。

**要做的事**：
- **README**：项目是什么、目标读者、环境要求（CUDA、TensorRT、OpenCV、CMake）；如何构建、如何运行（含典型命令：锚点、验证集、benchmark、stress）；数据与模型如何获取（公开数据集链接、engine 自行导出或下载）；文档与脚本索引。
- **LICENSE**：选一个（如 MIT、Apache-2.0），在仓库根放 LICENSE 文件。
- **.gitignore**：忽略 build、__pycache__、*.pyc、大文件（如 data/、*.engine、*.onnx 按需）；大文件用 Release 或脚本下载说明替代。
- **文档索引**：在 README 或单独 doc 中列出「部署流水线、推理流程、性能瓶颈、前后处理对照、单元测试、导出说明」等，便于按阶段查阅。

**产出**：README.md、LICENSE、.gitignore、文档索引；必要时「数据与模型获取」的一小段或脚本。

**常见坑**：README 太简略导致别人卡在环境或路径；未说明 engine 与 CUDA/TRT 版本绑定；大文件传仓库导致 clone 慢。

**本 demo**：目前无根目录 README，建议补；docs/ 下已有推理流程、性能瓶颈、前后处理对照、单元测试、导出相关文档；可把本「部署流水线操作指南」作为总索引。
