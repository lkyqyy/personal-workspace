# 扩展计划：多模型与并发

在现有单模型、单线程推理基础上，分阶段扩展为「多模型 + 并发 + 可选服务化」，提升可陈述性与复杂度。

---

## 扩展目标与阶段

| 阶段 | 目标 | 可陈述点 |
|------|------|----------|
| **Phase 1** | 多模型支持：按 ID 加载多个 engine，推理时指定模型 | 支持多模型加载与按需选择，为多任务/多算法并存打基础 |
| **Phase 2** | 并发：线程池 + 任务队列，多路请求并行推理 | 通过线程池与任务队列实现多路数据/多模型并发，提升吞吐 |
| **Phase 3** | 二选一：**(A) 推理服务** 或 **(B) 多线程流水线** | (A) 封装为 gRPC/HTTP 服务；(B) 预处理与推理流水线重叠 |

---

## Phase 1：多模型支持

**设计**：

- 新增 **ModelManager**（或等价类）：内部 `std::map<std::string, std::unique_ptr<InferenceEngine>>`，key 为模型 ID（如 `"fp16"`、`"fp32"`）。
- 接口：
  - `bool registerModel(const std::string& model_id, const std::string& engine_path);`  // 加载并注册
  - `bool predict(const std::string& model_id, const cv::Mat& img, cv::Mat& mask_out);`  // 按 ID 选引擎推理
  - `std::vector<std::string> listModels() const;`  // 列出已加载模型
- main / 调用方：启动时按配置注册多个 engine（如 fp16、fp32 各一个），后续按 `model_id` 调用。

**关键改动**：

- 新增 `include/ModelManager.hpp`、`src/ModelManager.cpp`。
- main：用 ModelManager 替代单 InferenceEngine；锚点/benchmark/stress 可加 `--model <id>` 指定模型。
- CMakeLists：把 ModelManager 加入编译。

**不破坏现有**：保留单 engine 用法（如 `ModelManager` 只注册一个 `"default"` 时行为与现在一致）。

---

## Phase 2：并发（线程池 + 任务队列）

**设计**：

- **任务**：`struct InferTask { cv::Mat img; std::string model_id; std::promise<cv::Mat> result; };` 或等价（含可选 callback）。
- **队列**：`BlockingQueue<InferTask>`（有界队列，防止堆积）。
- **线程池**：N 个 worker 线程，循环从队列取任务，调用 `ModelManager::predict(task.model_id, task.img, mask)`，将 mask 写回 `task.result` 或 callback。
- **提交接口**：`std::future<cv::Mat> submit(const std::string& model_id, cv::Mat img);` 或 `void submit(..., std::function<void(cv::Mat)> callback);`。

**关键改动**：

- 新增 `include/InferQueue.hpp`、`src/InferQueue.cpp`（或 InferPool），内部持有一个 ModelManager、一个队列、一组 worker 线程。
- main：可加 `--server` 或 `--concurrent <N>` 进入「并发模式」：主线程往队列丢任务（如从验证集循环读图），统计吞吐与延迟。
- 注意：每个 worker 若共用一个 InferenceEngine，TensorRT 多线程需每线程一个 context 或加锁；**建议每 worker 一个 InferenceEngine 实例**（同一 model_id 可共享同一 engine 文件，但 context 各建一份），显存占用 = 单模型 × worker 数。

**可陈述**：多路请求并发推理、有界队列与背压、吞吐随 worker 数变化（可做小实验）。

---

## Phase 3A：推理服务（gRPC 或 HTTP）

**设计**：

- 用 gRPC 或 HTTP（如 libhv、cpp-httplib）提供接口：**上传图像 → 可选 model_id → 返回 mask（二进制或 base64）**。
- 服务内持有一个 **InferQueue**（Phase 2），请求到达时 `submit(model_id, img)`，设置超时（如 5s），`future.get()` 或 callback 里把结果写回响应。
- 可选：健康检查、并发数限制、graceful shutdown。

**关键改动**：

- 新增 `src/server_main.cpp` 或 `server/` 目录，依赖 gRPC 或 HTTP 库；CMake 可选编译。
- 配置：端口、worker 数、默认 model_id、超时时间。

**可陈述**：将推理封装为服务、支持并发与超时、可被其他系统调用。

---

## Phase 3B：多线程流水线（预处理与推理重叠）

**设计**：

- **预处理线程**：循环读图（或从队列取路径），做 Preprocessor::process，将 `(input_tensor, ImageInfo)` 放入有界队列 A。
- **推理+后处理线程**：从队列 A 取，H2D → enqueueV2 → D2H → Postprocessor，将 mask 放入队列 B 或写回。
- **双缓冲**：至少两套 input_tensor / prob_out，轮换使用，避免每帧 new。
- 单模型即可，与 Phase 1 无强依赖；若与 Phase 2 共存，可「流水线 + 多 worker」结合（每个 worker 内是流水线）。

**关键改动**：

- 新增 `InferencePipeline` 或扩展现有 main：两个线程 + 两个有界队列 + 双缓冲；benchmark 对比「流水线前/后」FPS。
- 文档：流水线时序图、实测 FPS 提升比例。

**可陈述**：实现 CPU–GPU 流水线，端到端吞吐提升 x%。

---

## 实现顺序建议

1. **Phase 1**：多模型。改动集中、易测，不依赖并发。
2. **Phase 2**：并发。依赖 Phase 1 的 ModelManager（或直接用多 InferenceEngine）；可先做「单模型 + 多 worker」再扩展多模型。
3. **Phase 3**：选 A（服务）或 B（流水线）。服务更偏「系统/后端」可陈述；流水线更偏「性能」可陈述。
