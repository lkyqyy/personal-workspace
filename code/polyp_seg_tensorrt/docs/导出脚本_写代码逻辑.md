# 导出 ONNX 脚本的写代码逻辑：动机 → 步骤 → 结果

**范围说明**：本文档仅针对「把 .pt 导出为 .onnx」的**这一脚本**（如 `export_pt_to_onnx.py`）的写代码逻辑，不涉及整个高性能推理仓库（TensorRT 编译、C++ 推理、部署服务等均不在本文档内）。

下面说明写这段导出脚本时要写哪些内容、先写什么后写什么、每一步要考虑什么、预期是什么。按**动机 → 步骤 → 结果**组织；每一步末尾标明**对应脚本**（`scripts/export_pt_to_onnx.py` 中的类名/函数名与行号），便于对照代码阅读或修改。写或改脚本时，建议同时对照**「注意事项与避雷」**一节（容易忽略什么、避雷的坑、关键操作）。

---

## 一、动机（为什么要写这段代码）

- **要解决的问题**：把训练好的 PyTorch UNet 权重（.pt）导出成 ONNX，供 TensorRT 等推理引擎使用；导出过程要可复现、与训练结构一致，且兼顾 TensorRT 的精度与性能要求。
- **不写的后果**：直接 `torch.onnx.export` 容易在 Resize、Sigmoid、eval、输入尺寸等方面埋坑，导致 TensorRT 推理掉点或解析失败；没有统一脚本则每次导出依赖手敲命令、参数易错、别人难以复现。
- **写完之后要得到什么**：一个可复用的脚本，输入 .pt 和少量参数，输出正确、可被 TensorRT 解析的 .onnx，且导出选项（sigmoid、简化、固定/动态输入）可配置。

---

### 第 1 步：模型定义（与训练完全一致）

**对应脚本**：`scripts/export_pt_to_onnx.py` — `DoubleConv`（约 41–56 行）、`Down`（59–71）、`Up`（74–95）、`OutConv`（97–104）、`UNet`（107–145）、`UNetWithSigmoid`（148–156）。

**要写的内容**  
- 与训练脚本里**完全一致**的 UNet 结构：DoubleConv、Down、Up、OutConv、UNet（含 forward）。  
- 若支持「输出端包 Sigmoid」的选项，再写一个 UNetWithSigmoid 包装类（forward 里先调 unet 再 sigmoid）。

**先写什么、后写什么**  
- 先写底层模块：DoubleConv → Down → Up → OutConv。  
- 再写 UNet（依赖上述模块）。  
- 最后写 UNetWithSigmoid（依赖 UNet）。

**要考虑什么**  
- 训练时上采样是 bilinear 还是 ConvTranspose2d？Up 里要分支一致；bilinear 时**显式**写清 `align_corners=False`，便于后续和 TensorRT/Netron 对齐。  
- 训练时有没有 Dropout、Identity？**Dropout** 在 `model.eval()` 下会关闭（相当于输出=输入，不做任何有用计算），导出到 ONNX 只会多出无用节点；**Identity** 就是 y=x，推理时完全不参与计算。这类「推理时等价于直通、不改变结果」的层不要写进导出用模型，否则图更复杂、TensorRT 解析/优化时多绕一圈，没意义。本脚本里的 UNet 本身就没有这两类层，所以无需删。  
- 输出是 logits 还是已经过 sigmoid？若只导出 logits，Sigmoid 留给 UNetWithSigmoid 可选包一层。

**预期**  
- 用与训练相同的输入形状跑一次 `model(dummy_input)`，输出 shape 正确（如 1×1×H×W），且能与训练脚本里同一结构的 `state_dict` 一一对应。

**验证方式**  
- **Shape**：`dummy = torch.randn(1, 3, H, W)`，`out = model(dummy)`，断言 `out.shape == (1, 1, H, W)`。  
- **state_dict 对应**：加载 .pt 后，`list(model.state_dict().keys())` 与训练脚本里同结构模型的 keys 完全一致，且每层 shape 一致（可写一小段比对 keys + 每 tensor 的 shape）。  
- **数值一致（可选）**：用同一份 dummy 输入、同一 .pt，在训练环境与导出脚本里各跑一次 forward，比对两边的 `out`（如 `torch.allclose(a, b)` 或 `(a - b).abs().max()` < 1e-5），确认导出用模型与训练模型计算一致。

### 第 2 步：加载 .pt（checkpoint 格式兼容）

**对应脚本**：`scripts/export_pt_to_onnx.py` — 函数 `load_checkpoint`（约 159–185 行）。

**要写的内容**  
- 一个函数：输入 .pt 路径、device、以及 n_channels / n_classes / bilinear 等与训练一致的参数；输出已加载权重且 `eval()` 过的 model，以及 checkpoint 里除 state_dict 外的字段（若有）。

**先写什么、后写什么**  
- 先 `torch.load` 得到对象。  
- 再判断是「纯 state_dict」还是「含 'state_dict' 的字典」，分别取出 state_dict。  
- 用第 1 步的 UNet 构造模型，`load_state_dict(..., strict=True)`，再 `model.to(device).eval()`。

**要考虑什么**  
- 训练保存的是 `state_dict` 还是 `{'state_dict': ..., 'epoch': ...}`？两种都要能读，否则别人换一种保存方式就报错。  
- bilinear / n_channels / n_classes 必须和训练一致，否则 load_state_dict 可能静默错位或 strict=True 报错。  
- 加载后**必须** `model.eval()`，否则 BatchNorm 等行为与推理不一致，导出 ONNX 后再转 TensorRT 容易掉点。

**预期**  
- 对现有 .pt 调用该函数，不报错，且用同一 dummy 输入时，输出与训练环境里加载同一 .pt 的数值一致（可选做一次数值对比）。

---

### 第 3 步：命令行参数

**对应脚本**：`scripts/export_pt_to_onnx.py` — 函数 `parse_args`（约 235–248 行）。

**要写的内容**  
- argparse：--pt、--onnx（必填），--height、--width、--opset、--bilinear、--sigmoid、--simplify、--dynamic、--batch、--device 等。

**先写什么、后写什么**  
- 先写必填和与「导出形状/格式」强相关的（pt、onnx、height、width、opset）。  
- 再写与「模型行为」相关的（bilinear、sigmoid）。  
- 最后写可选优化与设备（simplify、dynamic、batch、device）。

**要考虑什么**  
- height/width 默认值要与训练常用分辨率一致（如 352），避免用户忘传导致导出尺寸错。  
- **先考虑固定分辨率 + 多 batch**：--batch 在非 dynamic 时有效，推荐多张图一次推理时显式传（如 --batch 4）；opset 建议默认 14。  
- 若脚本里会调 onnxsim，--simplify 要注明「需安装 onnx-simplifier」，未安装时脚本应友好提示而非崩溃。

**预期**  
- 用户可以通过命令行指定所有「与训练一致」和「与 TensorRT 需求一致」的选项，无需改代码。

---

### 第 4 步：导出 ONNX（固定/动态、常量折叠）

**对应脚本**：`scripts/export_pt_to_onnx.py` — 函数 `export_onnx`（约 188–232 行）。

**要写的内容**  
- 一个函数：输入 model、onnx 路径、height、width、batch_size、opset、是否 dynamic、device；内部构造 dummy 输入，调用 `torch.onnx.export`，并**开启 do_constant_folding=True**。

**先写什么、后写什么**  
- 先保证 model 已在目标 device 上且已 `model.eval()`。  
- 再根据是否 dynamic 构造 dummy 和 dynamic_axes（若需要）。  
- 最后调用 `torch.onnx.export`，写死 input_names/output_names（如 input、output），便于后续 C++/TensorRT 对接。

**要考虑什么**  
- **先考虑固定分辨率 + 多 batch**：固定 H/W 有利于 TensorRT 选 kernel，用 batch_size 指定 batch（如 4）；确需多分辨率或动态 batch 再用 dynamic。  
- Resize（Upsample）在 ONNX 里的行为依赖 PyTorch 的 align_corners 等，已在第 1 步模型里写死；这里不再改，只保证导出时用到的形状与训练一致。  
- 导出前再次 `model.eval()` 一次，防止前面某处漏调。

**预期**  
- 得到 .onnx 文件；用 Netron 打开可见输入/输出 shape 正确，Resize 等节点存在且属性符合预期（如 coordinate_transformation_mode）。

---

### 第 5 步：可选 ONNX 简化（onnxsim）

**对应脚本**：`scripts/export_pt_to_onnx.py` — 函数 `_run_onnx_simplifier`（约 286–303 行）。

**要写的内容**  
- 一个函数：输入 onnx 路径；若已安装 onnx-simplifier，则 load → simplify → 校验通过则覆盖原文件，否则另存为 xxx_simplified.onnx 并提示；未安装则打印「请 pip install onnx-simplifier」并直接返回。

**先写什么、后写什么**  
- 先 try import onnx 与 onnxsim，失败则提示并 return。  
- 再 onnx.load → simplify → 根据 check 决定覆盖还是另存。  
- 不改变导出脚本的主流程：简化失败或未安装都不应导致「没有 ONNX」；主流程始终以「第 4 步已生成的 .onnx」为准。

**要考虑什么**  
- simplify 可能改变图结构，校验未通过时不要覆盖原 ONNX，保留用户可用的那一份。  
- 依赖可选：脚本在无 onnx-simplifier 时仍能完成「导出 ONNX」，只是不自动简化。

**预期**  
- 加 --simplify 且安装 onnx-simplifier 时，用户得到简化后的 .onnx（或明确的 _simplified 副本）；未安装时脚本正常结束并提示，不报错。

---

### 第 6 步：主流程串联与提示

**对应脚本**：`scripts/export_pt_to_onnx.py` — 函数 `main`（约 251–284 行）；入口 `if __name__ == "__main__": main()`（306–307 行）。

**要写的内容**  
- main：解析参数 → 检查 .pt 存在、创建输出目录 → 调第 2 步加载模型 → 若 --sigmoid 则包一层 UNetWithSigmoid 并 eval → 调第 4 步导出 → 若 --simplify 则调第 5 步 → 打印一行「推理时 mean/std、通道顺序要与训练一致」的提醒。

**先写什么、后写什么**  
- 顺序严格：参数 → 检查/目录 → 加载 → 可选包装 → 导出 → 可选简化 → 提醒。  
- 不要先导出再加载，也不要先简化再导出。

**要考虑什么**  
- 用户可能误传不存在的 .pt 或只读目录；尽早检查并给出明确报错。  
- 提醒内容要具体：mean/std 与 Normalize 一致、BGR→RGB 在 C++ 侧做，避免用户推理时预处理不一致导致掉点。

**预期**  
- 一条命令即可完成「从 .pt 到 .onnx（及可选简化）」；控制台有清晰成功信息与一行预处理提醒。

## 注意事项与避雷（容易忽略的点、关键操作）

写或改导出脚本时，下面这些**容易忽略**、**一踩就雷**、以及**必须做到**的点，建议逐条对照。

### 容易忽略什么

| 步骤 | 容易忽略的 | 后果 |
|------|------------|------|
| 1 | 训练时是 bilinear 还是 ConvTranspose2d 没对上 | 解码器通道数不一致，`load_state_dict` 报错或静默错位；导出 ONNX 后 Resize 行为与训练不一致，推理掉点。 |
| 1 | Up 里 `align_corners` 没显式写死 | TensorRT/Netron 与 PyTorch 对齐时对不上，上采样边界易掉点。 |
| 2 | 只支持「纯 state_dict」一种保存格式 | 训练脚本若保存的是 `{'state_dict': ..., 'epoch': ...}`，直接报错或取错对象。 |
| 2 | 加载后忘记 `model.eval()` | BatchNorm 仍按训练行为，导出 ONNX 再转 TensorRT 后推理结果与训练时 eval 不一致，难以排查。 |
| 3 | height/width 默认值与训练不一致 | 用户不传时导出尺寸错，推理时输入 shape 对不上。 |
| 3 | --batch 与 --dynamic 同时传时语义未说明 | 脚本里 dynamic 优先时，--batch 被忽略，用户误以为固定了 batch。 |
| 4 | 导出前没再调一次 `model.eval()` | 若前面某处漏调或包装后未 eval，BatchNorm 等行为错误。 |
| 4 | 忘记开 `do_constant_folding=True` | ONNX 图多出冗余计算节点，TensorRT 解析/优化负担大。 |
| 5 | onnxsim 校验未通过时仍覆盖原 ONNX | 用户丢失一份可用的 .onnx，只能重新导出。 |
| 6 | 不检查 .pt 文件是否存在 | 报错靠 `torch.load` 或 `load_state_dict`，信息不直观。 |
| 6 | 不打印预处理提醒 | 推理端 mean/std 或 BGR/RGB 与训练不一致导致掉点，难以想到是预处理问题。 |

### 避雷的坑

- **模型结构与训练不一致**：多一层、少一层、或子模块命名不同（如 `outc.conv` vs `outc`），`load_state_dict(..., strict=True)` 会报错；若改成 `strict=False` 又可能静默漏加载，推理结果错。解决：导出用模型与训练脚本里 UNet **逐层对齐**，不要复制别的项目改改就用。  
- **bilinear 传反**：训练时是 bilinear，导出时没加 `--bilinear`（或反之），解码器通道数对不上，load 报错。解决：先确认训练脚本里 UNet 的 `bilinear` 参数，再与命令行一致。  
- **训练保存的是完整模型而非 state_dict**：如 `torch.save(model, path)`，则 `torch.load` 得到的是整个 model，没有 `state_dict` 键。解决：要么在加载逻辑里兼容「若已是 nn.Module 则取 .state_dict()」，要么在文档/脚本里明确只支持 `state_dict` 或含 `state_dict` 的字典。  
- **dynamic 与固定 batch 混用**：若实现上 `dynamic=True` 时忽略 `--batch`，用户传了 `--batch 4 --dynamic` 会误以为固定了 batch=4。解决：文档和 help 里写清「加 --dynamic 后为动态轴，--batch 仅在不加 --dynamic 时有效」。  
- **导出后从不做数值校验**：改完模型或加载逻辑后直接交给 TensorRT，推理掉点再回头查，很难定位是导出错还是预处理/后处理错。解决：至少做一次「同一 dummy、同一 .pt，训练环境 vs 导出脚本」的 forward 比对（如 `torch.allclose`），确认一致再转 TensorRT。  

### 关键操作（必须做的）

- **第 1 步**：模型与训练**完全一致**（层名、顺序、bilinear）；bilinear 时 Up 里**显式**写 `align_corners=False`。  
- **第 2 步**：支持「纯 state_dict」与「含 'state_dict' 的字典」两种格式；加载后**必须** `model.eval()`。  
- **第 3 步**：height/width 默认与训练常用分辨率一致；--simplify 未安装时**友好提示**、不崩溃。  
- **第 4 步**：导出前**再次** `model.eval()`；`torch.onnx.export` **必须** `do_constant_folding=True`。  
- **第 5 步**：onnxsim 校验**未通过**时**不覆盖**原 ONNX，只另存 _simplified 并提示。  
- **第 6 步**：**先检查** .pt 是否存在再加载；**打印**一行「推理时 mean/std、通道顺序要与训练一致」的提醒。

## 三、结果（写完之后得到什么）

- **可交付物**：仅此一个脚本（如 `export_pt_to_onnx.py`），依赖仅 torch（及可选的 onnx、onnxsim）；输入 .pt + 若干参数，输出 .onnx；行为可由命令行完全配置，无需改代码。不包含 TensorRT 编译、C++ 推理等其它仓库内容。
- **质量预期**：  
  - 与训练脚本里的 UNet 结构、bilinear、输入尺寸一致，能稳定加载现有 .pt。  
  - 导出的 ONNX 可被后续 TensorRT 等工具解析，Resize/Sigmoid 等选项符合「操作流水线」文档里对导出阶段的约定。  
  - 使用者按「操作流水线」运行本脚本即可得到 .onnx，无需猜脚本内部书写顺序。
