# 推理流程性能瓶颈分析

## 1. 运行方式

在项目根目录执行：

```bash
./bin/PolypSegmentationTRT --benchmark [轮数]
```

- **轮数**：验证集遍历次数，默认 20。即「验证集每张图跑一次」重复 20 轮，总样本数 = 图像数 × 轮数。
- 使用**完整验证集** `data/images/` 下所有 jpg/png（按文件名排序）。
- 先对前 10 张（或不足时全部）做 warmup，再按轮数 × 验证集逐张 `predictWithTiming`，统计均值与标准差。

## 2. 输出含义

示例输出（FP16 engine，256×256 输入，验证集 10 轮，7040 samples）：

```
[Benchmark] validation set, 704 images x 10 rounds (warmup 10), 7040 samples
  Stage       | Mean (ms) | Std (ms) | % of total
  ------------|-----------|----------|------------
  Preprocess  |    0.969 |   0.077 | 17.6%
  Inference   |    4.391 |   0.822 | 79.7%
  Postprocess  |    0.150 |   0.064 | 2.7%
  ------------|-----------|----------|------------
  Total       |    5.510 | (end-to-end)
  Bottleneck  | Inference (GPU)
```

- **Mean (ms)**：该阶段平均耗时（毫秒）。
- **Std (ms)**：标准差，用于看波动。
- **% of total**：该阶段占端到端总时间的比例。
- **Bottleneck**：耗时最大的阶段，用于指导优化重点。

**实测参考**：在完整验证集上（FP16、256×256），端到端约 4.2–5.5 ms/张（随轮数/负载略有波动），瓶颈在 GPU 推理（约 73–80%）；预处理约 18–24%，后处理约 2.7–3.6%，CPU 非主要瓶颈。

## 3. 三阶段对应关系

| 阶段        | 含义           | 对应代码 |
|-------------|----------------|----------|
| Preprocess  | 预处理（CPU）   | `Preprocessor::process`：letterbox、PIL 风格 resize、归一化 |
| Inference   | 推理（GPU）     | `predictRaw`：H2D、TensorRT enqueueV2、D2H |
| Postprocess | 后处理（CPU）   | `Postprocessor::process_with_info`：裁边、二值化、resize 回原图 |

计时在 `InferenceEngine::predictWithTiming` 中完成，与 `predict()` 逻辑一致，仅多一次高精度时钟采样。

## 4. 优化方向建议

- **Bottleneck = Inference (GPU)**  
  主要耗时在 GPU 计算与拷贝。可考虑：保持 FP16、检查输入尺寸是否可再缩小、或批量推理（若支持 batch）。

- **Bottleneck = Preprocess (CPU)**  
  主要耗时在 resize/归一化。可考虑：多线程/流水线、更轻量 resize、或 GPU 预处理（需改 pipeline）。

- **Bottleneck = Postprocess (CPU)**  
  主要耗时在裁边、二值化、resize 回原图。可考虑：多线程、减少 resize 次数、或与下一张图的预处理重叠（流水线）。

典型情况下（256×256、FP16），推理阶段约占 73–80%，预处理约 17–24%，后处理约 2.7–3.6%。若某 CPU 阶段占比异常高，可再针对性测单步（如仅 resize 或仅归一化）。

## 5. 压力测试（四维）

目标：在极限负载、长时间运行与异常输入下，验证**健壮性与确定性**，确保少量精度损失（如 2.91%）不会演变为生产事故。

### 5.1 吞吐量与时延（Throughput & Latency）

**运行：** `./bin/PolypSegmentationTRT --stress [秒数]`，默认 600 秒（10 分钟）。

- **QPS / FPS**：持续向引擎喂验证集图像（循环模拟视频流），结束时输出总帧数、总耗时、平均 FPS（即峰值处理速度）。
- **Latency 稳定性**：程序每 50 帧采样一次端到端耗时，结束时输出 **mean / P99 / max**（毫秒）。若平均 5ms 但 P99 或 max 出现明显“毛刺”（如 200ms），在实时场景不可接受。
- **按分钟 FPS**：每满 60 秒打印一次「过去 60s 的 FPS」，用于观察长时间下是否稳定。

**实测参考**（FP16、RTX 4060 Ti，`--stress 120`）：

```
[Stress] 704 images, 120 s (throughput + latency P99 + FPS/min)
  Tip: run "watch -n 1 nvidia-smi" in another terminal to monitor VRAM.
  [1 min] FPS (last 60s): 289.01
  ---
  Frames: 34632  Elapsed: 120.00 s  FPS: 288.59
  Errors: 0
  Latency: mean 3.48 ms  P99 4.18 ms  max 15.88 ms  (n=693)
```

吞吐稳定（~289 FPS）、无错误；P99 与 mean 接近，仅 max 偶发约 16 ms 毛刺，可接受。长时间压测可再观察按分钟 FPS 是否随温度下降、显存是否平稳。

**显存监控**：另开终端运行 `watch -n 1 nvidia-smi`，观察显存占用是否随运行时间**线性增长**；若增长则存在泄漏（如 cudaFree / IExecutionContext 未正确释放）。

### 5.2 内存与显存边界

- **显存稳定性（VRAM Leak）**：同上，用 `nvidia-smi` 观察。长时间 `--stress` 后显存应稳定在固定值，不应持续上升。
- **主机内存边界（OOM）**：当前 Preprocessor 使用固定尺寸（256×256）和栈上/堆上小缓冲，正常不会因单张图申请超大块；极端输入（如 10000×10）已在引擎侧拒绝（见 5.4）。若需模拟“仅剩 100MB”可结合 cgroups 或 ulimit 做系统级压测，属环境配置而非本程序单测。

### 5.3 热稳定性与降频（Thermal Throttling）

- **方法**：连续满载 `--stress 3600`（1 小时）或 `--stress 7200`（2 小时）。
- **观察**：看按分钟输出的 FPS。若随温度升高，FPS 从稳定值明显掉到更低（如 60→30），说明 GPU 降频；需从散热或功耗策略上优化。
- **精度**：高温导致硬件计算扰动极少见；若需严谨验证，可在压测前后对同一批图跑 Dice/IoU，确认仍在 0.79 左右。

### 5.4 异常数据抗压（Robustness to Garbage Data）

**运行：** `./bin/PolypSegmentationTRT --stress-robustness`

对以下输入做一次 `predict()`，期望**不崩溃**，且对非法输入返回 `false`、对合法异常图（全黑/全白）返回 `true`：

| 用例 | 说明 | 期望 |
|------|------|------|
| empty Mat | 空图 | false，不崩溃 |
| all black 256×256 | 传感器失效/全黑 | true，不崩溃 |
| all white 256×256 | 全白 | true，不崩溃 |
| extreme 10000×10 | 极端长宽比、超 8192 | false（引擎拒绝 >8192），不崩溃 |
| 0 rows / 0 cols | 非法尺寸 | false，不崩溃 |

引擎侧已做输入防护：空图、0 行列、单边 >8192 的图直接返回 `false`，避免 letterbox 除零或超大显存申请。
