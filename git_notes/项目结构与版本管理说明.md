# 项目结构与版本管理说明

基于「代码用 Git、数据用 DVC」的最佳实践，说明如何组织 ML/DL 项目，便于协作与复现。

---

## 1. 整体关系

- **Git 仓库**：管理代码、配置、以及**测试集/数据的变更记录**（如路径、版本指针），不存大文件。
- **DVC 远程仓库**：存放**测试集等数据的实际文件**，通过 DVC 与本地 `data/` 关联。
- **项目目录**：在本地按统一结构组织代码、数据引用、测试和脚本。

---

## 2. 推荐项目结构

```
project/
├── .git/                    # Git 元数据
├── .dvc/                    # DVC 配置与缓存信息
├── .github/                 # CI 配置（如 GitHub Actions）
├── data/                    # 数据目录（由 DVC 管理）
│   ├── base_test_set/       # 基础测试集
│   ├── edge_cases/          # 边界/困难样本
│   └── performance_test/    # 性能测试数据
├── tests/                   # 测试脚本
│   ├── unit/                # 单元测试
│   ├── integration/         # 集成测试
│   └── performance/         # 性能测试
├── scripts/                 # 工具脚本
│   ├── prepare_test_data.py # 准备/预处理测试数据
│   └── analyze_results.py   # 分析评估结果
├── .gitignore
├── dvc.yaml                 # DVC 流水线定义（数据/训练流程）
├── requirements.txt         # 依赖
└── README.md
```

要点：
- 代码、配置、测试脚本、DVC 指针 → 进 **Git**。
- 大体积数据（尤其测试集）→ 进 **DVC**，本地 `data/` 多为 DVC 管理的引用。

---

## 3. 各目录职责

| 路径 | 说明 |
|------|------|
| `data/` | 由 DVC 管理；可含 base_test_set、edge_cases、performance_test 等，便于区分用途与版本。 |
| `tests/unit/` | 单函数/单模块测试。 |
| `tests/integration/` | 多模块联合测试（如数据加载 + 模型前向）。 |
| `tests/performance/` | 推理速度、显存等性能测试。 |
| `scripts/` | 数据准备、结果分析等一次性或定期执行的脚本。 |
| `dvc.yaml` | 定义数据流水线或训练流水线，保证可复现。 |
| `requirements.txt` | 固定依赖版本，便于环境复现。 |

---

## 4. 与当前 PointINS 项目的对应

本仓库（pointins）可逐步向上述结构靠拢：

- **代码与配置**：`src/`、`scripts/`、`configs/` 等继续用 Git 管理。
- **数据**：若测试集/验证集较大，可迁入 `data/`，用 DVC 跟踪，例如：
  - `data/base_test_set/`：常规验证集
  - `data/edge_cases/`：掩码坍缩、小目标等困难样本，用于定性分析与逻辑校验
- **测试**：在 `tests/` 下可增加：
  - `unit/`：如 `validation_utils`、`color_affinity_loss` 等工具与损失的单元测试
  - `integration/`：数据加载 → 模型 forward → 损失计算 的集成测试
  - `performance/`：推理耗时、显存占用等
- **脚本**：`scripts/prepare_test_data.py`、`scripts/analyze_results.py` 对应数据准备与结果分析；现有 `train.py`、`test.py` 可保留在 `scripts/`。
- **复现**：通过 `dvc.yaml` 描述「数据 → 训练 → 评估」流水线，配合 `requirements.txt` 和文档，便于复现实验。

---

## 5. 使用时的注意点

1. **大文件不要直接提交 Git**：用 `.gitignore` 忽略原始数据目录，仅提交 DVC 生成的 `.dvc` 指针文件。
2. **数据版本**：每次更新测试集或重要数据时，用 `dvc add` / `dvc push` 更新指针并推送到 DVC 远程，再在 Git 中提交对应的 `.dvc` 变更。
3. **CI**：在 `.github/` 的 CI 中可拉取 DVC 数据后跑 `tests/` 与部分 `scripts/`，保证代码与数据版本一致。

---

## 6. 小结

- **Git**：代码、配置、测试脚本、数据**变更记录**（DVC 指针）。
- **DVC**：测试集等**实际数据**的存储与版本管理。
- 项目内用统一的 `data/`、`tests/`、`scripts/` 结构，配合 `dvc.yaml` 和 `requirements.txt`，有利于长期维护和实验复现。

当前仓库已具备 `src/`、`scripts/`、`README.md`、`requirements.txt` 等基础，后续可按需增加 `data/`（DVC）、`tests/` 和 `dvc.yaml`，与上述结构对齐。
